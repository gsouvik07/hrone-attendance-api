# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 33-37) | Off-by-one strict grace period check (`minutes > 10`); if punch-in is 10 min 1 sec after shift start (e.g. 09:40:01 for 09:30 shift), `(punch_in - start).total_seconds() / 60` truncated to int is 10, and `10 > 10` evaluates to False, returning 0 instead of 10. Also, `punch_in.replace(...)` puts shift start on the punch-in calendar date, producing negative values for overnight shifts punching in past midnight. | Punch in at 09:40:01 IST for a 09:30 shift returned 0 late minutes instead of 10. Overnight shift punching in at 00:05 returned 0 or negative. | Truncated instant to whole seconds, aligned `shift_start` with the record's attendance date in IST, checked if elapsed seconds > 600, and returned `elapsed_seconds // 60`. |
| 2 | `compute_work_hours` (lines 40-41) | Uses Python's native `round()`, which performs banker's rounding (round-half-to-even) with float representation rather than half-up rounding. E.g., 2.675 hours rounds to 2.67 instead of 2.68. | A punch-out duration of 9630 seconds (2.675 hours) resulted in 2.67 instead of 2.68. | Replaced with `Decimal` arithmetic and `ROUND_HALF_UP` to 2 decimal places per R4. |
| 3 | `compute_overtime` (lines 44-47) | Missing R3 30-minute minimum threshold; returned any positive minutes (e.g. 10 or 15 min). Also assumed shift end falls on `date_str`, breaking overnight shifts where shift end falls on the next calendar day. | Punch-out 15 minutes after shift end returned 15 instead of 0. Overnight shift punch-out produced negative or incorrect overtime. | Added 1 day to `date_str` when `shift_end <= shift_start`, verified overtime seconds >= 1800 (30 minutes), and returned `ot_seconds // 60` or 0. |
| 4 | `health` (lines 72-74) | Returns `{"status": "ok"}` unconditionally without checking if MongoDB is reachable. | Stopping the MongoDB server still yielded HTTP 200 instead of 503. | Added `client.admin.command("ping")` in a try/except block; raises HTTP 503 on connection failure. |
| 5 | `create_employee` (lines 78-85) | Race condition due to check-then-insert without a unique index on `emp_code`. Also missing validation for customer `emp_code` regex, email format, and rule that `shift_start != shift_end`. `created_at` returned unformatted datetime rather than epoch milliseconds. | Concurrent POST requests with the same `emp_code` created duplicate records. Setting `shift_start` equal to `shift_end` succeeded. `created_at` returned an ISO string instead of integer epoch ms. | Created a unique index on `emp_code` at startup, handled `DuplicateKeyError` to return 409, added Pydantic validations, and converted `created_at` to integer epoch ms. |
| 6 | `list_employees` (lines 88-96) | Off-by-one page skip calculation: `skip = page * page_size`, which on page 1 skips the first 20 records. `total = count_documents({})` ignored the department filter. Results were not sorted by `emp_code` ascending. Missing pagination parameter bounds validation. | `GET /employees?page=1` skipped the first 20 employees. `GET /employees?department=Sales` returned total count of the entire collection. | Set `skip = (page - 1) * page_size`, filtered count with `count_documents(q)`, added `.sort("emp_code", 1)`, added Query range validations, and serialized timestamps. |
| 7 | `punch_in` (line 101) | Does not check if employee exists. If employee is not found, `emp["shift_start"]` on line 113 raises an unhandled `TypeError` (HTTP 500) instead of returning HTTP 404. | `POST /attendance/punch-in` with an unknown employee code returned 500 Internal Server Error. | Added check `if not emp: raise HTTPException(404, "Employee not found")`. |
| 8 | `punch_in` (lines 102-103) | `datetime.fromtimestamp(...)` creates a naive local datetime. `d = ts.date().isoformat()` ignores IST timezone and fails overnight shift rules where punch-in before shift end belongs to the previous day's shift. Fails to truncate instants to whole seconds (R1). | Punch-in for an overnight shift at 00:30 IST recorded the record under today's date rather than yesterday's shift start date. | Truncated timestamp to whole seconds, converted to IST, applied overnight shift logic against `shift_end`, and derived the correct attendance date. |
| 9 | `punch_in` (lines 104-118) | Check-then-insert concurrency race condition: two simultaneous punch-ins for the same employee and date both pass `find_one` and insert duplicate documents. | Concurrent punch-ins for the same employee and date resulted in duplicate records in the database. | Created unique compound index on `(emp_code, date)` and handled `DuplicateKeyError` to return HTTP 409. |
| 10 | `punch_in` (lines 109, 119) | Accepts invalid status values (such as `ABSENT` or `LEAVE`). Injects `doc["id"] = str(res.inserted_id)` which violates the OpenAPI contract (`id` is internal and must not appear in responses). Returns `punch_in` as datetime rather than epoch milliseconds. | Response contained an `"id"` field; `status` accepted invalid strings; `punch_in` was returned as datetime. | Enforced `PresenceStatus` enum (`PRESENT`, `WFH`, `ON_DUTY`), dropped `_id` without injecting `id`, and formatted `punch_in` as epoch milliseconds integer. |
| 11 | `list_attendance` (lines 125-150) | In-memory sorting and pagination: fetches the entire result set into memory (`docs = list(...)`), then sorts and slices in Python. At 100k documents this causes severe latency and memory exhaustion. Injected `"id"` into items. Did not validate `date_from > date_to`. | Querying attendance on large collections ran out of memory or caused high latency. Supplying `date_from > date_to` returned 200 with empty items instead of 422. | Replaced with database-level `.sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)`, validated date range, and omitted internal `_id`/`id`. |
| 12 | Instant serialization boundary | Instants were handled as unparsed datetimes in responses or naive datetimes on input without ensuring the integer epoch millisecond contract required by the specification. | API responses failed schema validation when expecting integer epoch milliseconds. | Created unified `dt_to_epoch_ms` and `epoch_ms_to_dt` boundary helpers to convert cleanly between BSON UTC datetimes and integer epoch milliseconds. |

Also note anything you looked at and decided was **not** a defect, and why:

1. **Shift Defaults**: The default values `"09:30"` for `shift_start` and `"18:30"` for `shift_end` match the OpenAPI schema defaults.
2. **Environment Variable Configuration**: Reading `MONGO_URI` and `MONGO_DB` from environment variables with fallback defaults is correct and adheres to the environment contract.
3. **1-Indexed Pagination**: Starting pagination with `page=1` complies with rule R10 and OpenAPI parameter definitions.
